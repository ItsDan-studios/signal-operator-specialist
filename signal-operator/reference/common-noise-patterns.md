# Common Noise Patterns

These are common traps the operator can suggest during onboarding and daily triage. Use them as possibilities, not verdicts.

## Overthinking

### What it looks like

Staying in analysis long after the next move is obvious.

### Why it is usually noise

It creates the feeling of seriousness without advancing execution.

### How to suggest it

`One common noise pattern here is overthinking - staying in analysis after the next move is already clear. Does that sound like what is happening, or is there a real unknown we still need to resolve?`

## Checking dashboards too early

### What it looks like

Refreshing metrics before enough data exists to make a useful decision.

### Why it is usually noise

Early data often creates movement without insight.

### How to suggest it

`Another common pattern is checking dashboards too early. If there is not enough data to make a call yet, this may be real work later but noise right now.`

## Planning to plan

### What it looks like

Building systems, schedules, or frameworks before the underlying work is active enough to need them.

### Why it is usually noise

It feels organized, but often delays the actual mission-moving work.

### How to suggest it

`This may be planning to plan - setting up structure before the live work actually requires it. Is the structure the bottleneck, or is execution the bottleneck?`

## Chasing every opportunity

### What it looks like

Promoting every interesting lead, idea, or request into active attention.

### Why it is usually noise

It fragments the board and weakens follow-through on the work already underway.

### How to suggest it

`A common trap here is chasing every opportunity. This might be real, but does it deserve one of the active slots right now or is it just asking for attention?`

## Tool / feature over-integration

### What it looks like

Adding new tools, features, or integrations to an internal system before they clearly improve execution.

### Why it is usually noise

It is productive-looking internal work that often outruns the actual business need.

### How to suggest it

`One common AI-builder pattern is over-integrating - wanting every new tool or feature inside the system before it has earned the time. Is this improving live execution, or is it satisfying curiosity?`

## Reacting to urgency that does not move the mission

### What it looks like

Treating every incoming pressure as if it deserves a signal slot.

### Why it is usually noise

Urgency is a clock. Signal is leverage. The two overlap sometimes, but not automatically.

### How to suggest it

`This has urgency, but urgency alone does not make it signal. Does it move the mission, remove a bottleneck, or unblock execution right now?`
